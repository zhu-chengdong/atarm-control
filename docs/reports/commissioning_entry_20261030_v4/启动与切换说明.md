# 从伪串口切换到实机的启动入口

2026-10-30 v4，独立派生于 v3。实机入口、默认禁用的参数模板与现场确认表已准备。本轮只在 Mark 工作站的隔离容器与测试自建 PTY 中验证，没有打开真实电机串口，没有连接相机/底盘，没有修改 PPT。原源码、v1—v3 和原实机流程保留。

## 1. 使用哪些文件

| 用途 | 文件 |
|---|---|
| Mark 工作站宿主入口，负责启动既有 ROS 容器 | 新开发副本的 `tools/commissioning_container.py` |
| 容器内配置检查与实机节点入口 | `python3 -m atarm_controller.commissioning_launcher` |
| 设备、网络、电源、停止及现场确认 | [site.template.json](../../../config/commissioning/site.template.json) |
| 四电机、控制模型、参考与视觉标定 | [session.template.json](../../../config/commissioning/session.template.json) |
| 与 Mark 逐项确认及填写依据 | [现场参数确认表](现场参数确认表.md) |
| 本轮实际检查及保留证据 | [离线验证记录](离线验证记录.md) |

入口分为 `check` 和 `run`。`check` 只读配置和库文件哈希，不加载原生库、不导入 ROS、不打开串口；宿主包装器为它启动无设备映射、无网络的只读容器。`run` 额外要求显式 `--connect-hardware`、完整参数和现场确认，并使用新的日志目录。

模板中所有未知实机值均为 `null`，`hardware_enabled=false`。已知的软件策略保留或明确列出，已构建实机能力库的路径和哈希已填入；它们不代表安装参数或实物测试通过。不要把旧 `offline_fd_validation.json` 改个名字当作现场标定。

## 2. 保留伪串口验证入口

原 `cartesian_fd_node --offline-pty` 入口和原生 PTY 库保留。新实机能力库单独构建并保存，不替换 `native/build/liba1_serial_adapter.so`，也不覆盖 v3 工作站目录。

本次构建产物在工作站：

```text
/home/zcd/codex-runs/atarm-commissioning-entry-20261030-01a1831d/results/build01/
  offline/liba1_serial_adapter.so
  physical/liba1_serial_adapter.so
  vendor/lib/libUnitreeMotorSDK_Linux64.so
```

每个库目录有 `build_receipt.json`，记录 SHA-256 和实机能力标志。实机模板使用 `/native/physical/liba1_serial_adapter.so`，宿主入口将上述构建目录只读映射成 `/native`。它会先核对哈希，再确认库导出的实机能力；离线库、旧库或哈希错误均不能用于实机启动。

## 3. 到场先填写和检查，暂不运行 run

继续使用已建立的 `elecpc-hppc` 工作站与 SSH 方式。宿主不需要重新安装 ROS，入口沿用已缓存的固定 Jazzy 镜像，不自动下载镜像、不安装包、不修改设备权限。

在工作站终端设定路径。以下是到场后使用的准备命令，本轮没有据此连接实物。

```bash
ARM_PROJECT=/home/zcd/codex-runs/atarm-commissioning-entry-20261030-01a1831d/project
NATIVE_DIR=/home/zcd/codex-runs/atarm-commissioning-entry-20261030-01a1831d/results/build01
SITE_DIR=/home/zcd/agri-arm-commissioning/site_$(date -u +%Y%m%dT%H%M%SZ)
```

复制到一个新现场目录，原模板不改。下方程序在目录或文件已存在时拒绝覆盖。

```bash
python3 - "$ARM_PROJECT" "$SITE_DIR" <<'PY'
import json,sys
from pathlib import Path
project,folder=map(Path,sys.argv[1:])
folder.mkdir(parents=True,exist_ok=False)
source=project/'config/commissioning'
site=json.loads((source/'site.template.json').read_text())
site['session_file']='session.json'
with (folder/'site.json').open('x') as f:json.dump(site,f,indent=2)
with (folder/'session.json').open('xb') as f:f.write((source/'session.template.json').read_bytes())
PY
```

然后按[参数确认表](现场参数确认表.md)填写 `site.json`、`session.json`。填写阶段继续保持 `hardware_enabled=false`；先完成 Mark 要求的新供电和基本动作验证，再记录机械、视觉、初始雅可比与限值的依据。

```bash
python3 "$ARM_PROJECT/tools/commissioning_container.py" check \
  --project "$ARM_PROJECT" --site-dir "$SITE_DIR" --native-dir "$NATIVE_DIR"
```

空模板应返回非零退出码，列出缺项，`ready_for_run=false`、`serial_devices_opened=false`。这表示拒绝条件正常生效。不要删除缺项让程序回退到模拟默认值，程序也不会接受这种回退。

`parameters_valid=true` 仅表示参数完整、内部一致且库哈希匹配。现场确认标记仍为 false 或 `hardware_enabled=false` 时，`ready_for_run` 仍为 false。只有所有确认真实完成后才填写姓名、日期、证据路径并改为 true。它们是试验记录，不能提前勾选。

## 4. 真正切换时由哪些检查把关

进入 `run` 前，宿主入口先在无设备容器里完成一次 `check`。通过后才在宿主只读检查两路稳定设备别名和 USB 身份，再映射恰好两路设备。实际控制容器使用 host 网络接收外部视觉，保留只读源码、配置和库目录，只允许本次日志目录写入。

运行时逐一检查 `/dev/serial/by-id/` 别名、USB 序列号、VID/PID、字符设备身份及两路是否指向同一设备；打开前后再核对身份。随后请求独占访问、设置经确认的串口参数并回读波特率。第二路失败时关闭已经取得的描述符和适配器，不留下半套启动资源。

当前串口实现仅支持 Linux x86_64、8N1、无硬件/软件流控，并要求适配器自动管理半双工方向。支持 Linux termios2 的显式自定义波特率，但**本次测试所用波特率不是对现场 A1 波特率的认定**。不满足这些条件时先补相应驱动支持，不能随便填成支持值。

独占请求不能踢掉先前已打开串口的其他程序。到场必须确认旧控制器、终端和其他实验进程已退出；程序不会自动杀进程、修改 udev、执行 chmod 或重新配置机器人网络。

这个入口是**已标定三维控制的启动入口**。首次电源/基本动作检查、物理参考建立和初始 J 数据采集，仍按既有实机流程使用 Mark 已确认的手动方式完成。它不提供自动归零、自动标定、自动展开或自动恢复。

## 5. 现场完成确认后才能执行的实机命令

以下命令会连接已配置的真实串口，本轮未执行。到场后由你在完成前述确认时使用，不属于现在的离线检查。

```bash
RUN_DIR=/home/zcd/agri-arm-commissioning/run_$(date -u +%Y%m%dT%H%M%SZ)
python3 "$ARM_PROJECT/tools/commissioning_container.py" run \
  --project "$ARM_PROJECT" --site-dir "$SITE_DIR" --native-dir "$NATIVE_DIR" \
  --run-dir "$RUN_DIR" --connect-hardware
```

若模板未填完或确认未完成，该命令仍会在打开串口前拒绝。去掉 `--connect-hardware` 也会拒绝。源码目录、构建目录和实机配置各自独立，没有把伪串口名称改成实物路径就自动上线的快捷模式。

启动后先观察命名空间内的状态。默认命名空间是 `/atarm_commissioning`；在使用同一 ROS_DOMAIN_ID、RMW 和已 source Jazzy 的 ROS2 工具终端中：

```bash
ros2 topic echo /atarm_commissioning/atarm/cartesian/state std_msgs/msg/String
```

初始应为 `UNCONFIRMED`，无自动位置运动。底层已有模式/零努力反馈请求，不能把“未自动展开”理解为完全没有设备报文。确认机械支撑和参考形态后，再显式提交参考检查：

```bash
ros2 service call /atarm_commissioning/atarm/cartesian/confirm_reference std_srvs/srv/Trigger '{}'
```

服务返回受理不代表 READY。必须等待稳定视觉窗口与四路实测索长检查通过。该操作将保持当前位置，不会把当前编码器清零，也不能替你证明机械形态正确。

之后才按原实机流程发送本次已测量的小幅三维目标；本说明没有提供可误抄的“实机目标坐标”。取消接口为：

```bash
ros2 service call /atarm_commissioning/atarm/cartesian/cancel std_srvs/srv/Trigger '{}'
```

三维目标、回执和状态仍使用 v3 契约，成功必须是最终 `SUCCEEDED` 且 `complete=true`。故障/取消后不能自动重试；先支撑并核查原因和参考，再结束会话。退出前也要先确保机构受支撑，当前退出策略发送零努力，不能替代承重制动。

## 6. 本次验证覆盖与现场仍需确认的范围

本轮检查了配置拒绝、显式连接门槛、两路身份先检查后打开、原生库能力/哈希、第二路失败回收、自建 PTY 上的实际 Linux 串口配置和 A1 协议，以及既有 ROS 控制回归。实机原生能力库仅被构建和在测试自建 PTY 上使用，没有连接实物。

物理 USB 适配器的真实通信、电机供电与承重保持、实际方向/零位/增益/行程、视觉尺度与外参、真实采样时延、三维 J 和到位误差均未测。电气限值在配置中用于明确现场要求和保存依据，软件没有电压/电流传感输入，不能自动监测或断电。停止策略及监护方式必须由你和 Mark 在现场确认。
